How Kubo reconciles a Stack

The flow

A Stack manifest lands in the cluster (from kubectl, ArgoCD, or the kubify-website SaaS portal). The kubo operator watches every Stack CR, pulls its OCI bundle, and installs components as Helm releases in dependency order — propagating secrets and reconciling Istio routing along the way.

The reconcile loop

Every change to a Stack — a new bundle tag, a values override, a pause, or a manual reconcile trigger — re-enters the same loop. Components are planned into dependency waves, deployed in order, and status rolls back up into the Stack CR.

Shared operators, tenant workloads

Cluster-scoped operators (Vault, Spark, Istio, …) install once into a shared operators namespace and watch every tenant namespace. Tenant charts never duplicate them — a tenant Stack declares which operators it needs, and the operator wires credentials, secrets, and routing across namespace boundaries.

Deployment modes

Direct

The operator's embedded Helm engine installs and upgrades releases itself, in dependency order. No extra moving parts — simplest path, full status detail per component.

spec.mode: Direct

Flux

The operator compiles each component into a Flux HelmRelease and hands execution to helm-controller. Choose it when the cluster already standardizes on Flux for GitOps continuity.

spec.mode: Flux

Bundle once, deploy anywhere

Bundles are plain OCI artifacts on any registry — ghcr.io included. Because a Stack references a bundle by URL, the same artifact deploys to any cluster: dev, staging, or a customer's AKS estate. Composition is by reference, so products can build on shared bundles without vendoring each other's charts.

Shared operators

Vault, Spark, Istio and friends install once per cluster into the operators namespace and watch every tenant namespace. Tenants get the operators they declare — never duplicate controllers, never cross-tenant coupling.
